Задание по проекту: комплект документов
Что подготовить по своей фиче и как это будет засчитано
По своей фиче каждая команда готовит четыре связанных документа. Это один сквозной путь: зачем → что → кто →
доказательство связности. Ценность — не в документах по отдельности, а в связке между ними.
Что подготовить и зачем
Документ Зачем его готовить
PRD — Product
Requirements Document
SRS — Software
Requirements
Specification
User Stories (+
критерии приёмки)
Зафиксировать «зачем»: проблему, аудиторию, метрики успеха и границы. Согласовать с командой, что
вообще стоит делать и как поймём, что получилось.
Перевести «зачем» в однозначное «что система должна делать»: проверяемые функциональные и
нефункциональные требования. Общий контракт для разработки и тестирования.
Описать функциональность глазами пользователя — «кто / что / зачем» — и задать проверяемое «готово»
(acceptance criteria). Единица планирования спринта в бэклоге.
RTM — Requirements
Traceability Matrix
Связать всё в цепочку и доказать полноту: каждое требование обосновано целью и покрыто тестом, ни одно
не потеряно. Основа для анализа влияния изменений.
Чек-лист сдачи
Документ засчитан, если в нём есть всё перечисленное.
PRD
☐ Краткое описание фичи (one-liner) — что и для кого
☐ Проблема с обоснованием (по возможности — данными)
☐ Метрики успеха: главная + прокси + guardrail
☐ Аудитория и явные non-goals (что НЕ делаем)
☐ Scope решения (What) — без ухода в реализацию
SRS
☐ Введение: назначение и scope (что входит / не входит)
☐ Общее описание: пользователи, допущения, зависимости, ограничения
☐ Функциональные требования с ID и критерием приёмки у каждого
☐ Нефункциональные требования (скорость, надёжность, безопасность…)
☐ Формулировки проверяемы: никаких «быстро / удобно» без метрики
User Stories
☐ Формат Connextra: роль → цель → выгода
☐ У каждой истории — ID и критерии приёмки (Given–When–Then)
☐ Истории небольшие (одна ценность = одна история)
☐ Трассировка US → требования SRS
RTM
☐ Перечислены все требования с ID
☐ У каждого — источник ↑ (US / бизнес-цель) и проверка ↓ (тест / метрика)
☐ Нет сирот: ни одного требования без обоснования или без покрытия
☐ Тест-кейсы привязаны к требованиям; бизнес-цели закрыты
Сквозной критерий (главный)
☐ Возьмите любое требование и пройдите его в обе стороны — вверх до бизнес-цели PRD, вниз до теста. Если цепочка рвётся
— работа не готова.
Планка намеренно минимальная: это проверка не «идеальных» документов, а того, что вы поняли связность PRD → SRS → US
→ RTM, а не просто заполнили шаблоны.
